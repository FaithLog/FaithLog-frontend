# 동물 관리와 기존 활동·미션 연동안

현재 코드 검토 기준: FaithLog 프론트 feature/315-companion-pages 및 백엔드 develop. 이 문서는 제안이며 아래 API·테이블은 아직 구현되지 않았다. 현재 동물 기능은 __DEV__에서만 노출하고 예시 포인트·보유 목록·미션을 세션 내에서 처리한다.

## 이번 관리 화면 개선

- 이름·의상·동물 종류 검색. 유니크 고유 이름도 동물 종류로 찾을 수 있다.
- 등급 필터와 기본순 / 희귀순 / 보유 많은 순 정렬.
- 수집 진행도와 판매할 수 있는 중복 수량 표시.
- 상세를 열지 않고 목록에서 배치 / 해제. 5마리가 가득 차면 선택한 친구의 상세에서 교체할 친구를 고른다.
- 교체는 같은 슬롯·저장 위치를 이어받고 보유 수량과 포인트는 바꾸지 않는다.
- 중복 판매 수량에 '최대' 추가. 마지막 한 마리 유지와 확인 단계는 유지한다.
- 검색 결과 없음, 중복 없음, 보유 없음 안내를 구분. 판매로 목록 수가 줄어도 빈 마지막 페이지에 남지 않는다.

### 날짜 체크는 두 군데에서 저장된다

- `src/devotion/MonthlyCalendarScreen.tsx`의 빠른 체크 → `saveDevotionDailyCheck`.
- `src/devotion/DevotionScreen.tsx`의 임시저장·최종제출 → `saveWeeklyDevotion`에 날짜별 dailyChecks를 함께 저장.
- 한 화면에만 완료 처리를 붙이면 다른 화면에서 저장한 활동이 누락된다. 서버 판정은 공통 저장 데이터 기준으로 하고, 두 저장 경로 모두 성공 후 미션 조회를 무효화한다.
- 화면에서 체크를 눌렀다는 사실, 저장 전 formChecks, 실패한 HTTP 요청은 완료 증거가 아니다.
- 과거 날짜 기록을 오늘 수정해도 오늘의 일간 보상을 받게 하면 안 된다. 기존 기록 수정 기능은 유지하되 보상 대상 날짜·수령 기한을 별도로 검증한다.
- 일간 첫 버전은 서버의 '오늘' 기록만 보상 대상으로 제안한다. 과거 보상 소급 지급은 별도 정책으로 열기 전까지 하지 않는다.

### 주간 경건의 기본 주가 서로 다르다

`src/devotion/devotionDefaultWeek.ts`의 `resolveInitialDevotionWeek`는 전주 미제출이면 전주를 먼저 연다. 현재 데모의 `getMissionPeriodKeys`는 항상 현재 월요일을 주간 키로 쓴다. 따라서 현재 데모의 ready 판정을 실제 기록으로 바꾸는 것만으로는 올바르게 연결되지 않는다.

제안:

1. 서버 미션 응답에 `periodKey`, `targetWeekStartDate`, `claimableUntil`을 포함한다.
2. '제출하러 가기'는 서버가 지정한 주를 명시적으로 연다. 표시도 '11/2–11/8 경건 제출'처럼 대상 주를 드러낸다.
3. 일간 미션은 경건 기본 화면이 아니라 캘린더의 오늘 날짜를 연다.
4. 주간 제출 보상은 해당 기록의 주에 귀속한다. 전주 기록을 이번 주 제출해도 같은 주 기록으로 중복 보상하지 않는다.
5. 수령 유예 기간은 화면에서 임의로 추정하지 않고 서버 정책으로 응답한다. 1주 유예를 초기 제안으로 두되 정책 확정 후 적용한다.
6. 기존 화면을 덮어쓰지 않고 미션 진입 의도를 보존한다. 완료 후 '미션으로 돌아가기'로 같은 탭·대상 기간을 복원한다.

현재 `CompanionPages.onActivity`와 `FaithLogApp` 연결은 'devotion' / 'polls' 문자열만 전달한다. 다음 단계에서 `{screen:'calendar',recordDate}` / `{screen:'devotion',weekStartDate}` / `{screen:'polls',pollId?}` 형식으로 확장하고, 기존 `setDevotionInitialDate` 및 월간 캘린더 경로를 재사용한다. 전주 미제출 우선 선택은 명시적 날짜 없이 들어간 일반 경건 화면에서 그대로 유지한다.

### 투표 응답 시각은 수정될 수 있다

`PollScreen.submitResponse`는 저장 성공 후 상세·목록을 다시 조회한다. 목록의 `responded`에는 응답 시각이 없으므로 '현재 응답했음'을 '이번 주 참여'로 판단할 수 없다.

백엔드 `PollResponse.updateMemo`는 응답 수정 때도 `respondedAt`을 현재 시각으로 바꾼다. 전주 응답을 이번 주 수정하는 것만으로 주간 미션이 완료되지 않도록 최초 생성 시각 또는 최초 응답 이벤트를 기준으로 해야 한다. 현재 엔티티의 불변 `createdAt` 또는 별도 미션 활동 원장을 서버에서 조회한다. 과거 투표도 이번 주 처음 참여했다면 인정할지, 현재 주에 열린 투표만 인정할지는 서버의 대상 투표 목록으로 명시한다. 권장 초기 정책은 이번 주 최초 유효 응답 1건으로 주간 보상을 1회 지급하는 것이다.

### 벌금 없음과 미납 없음은 다르다

백엔드 `WeeklyDevotionCommandService`는 최종 제출 시 벌금을 계산하고, 0원이면 청구 행을 생성하지 않는다. 따라서 청구 내역이 비어 있다는 사실은 '벌금 0'의 충분한 증거가 아니다. 아직 미제출이거나 목록이 일부 페이지만 로딩됐을 수 있다.

- PAID라도 벌금이 발생했다면 '벌금 없음'에 해당하지 않는다.
- 커피·식사 청구와 경건 벌금을 구분한다.
- 미제출, 집계 중, API 실패는 완료로 바꾸지 않는다.
- 제출 시 계산한 벌금 결과를 주별 확정 결과로 보존하거나, 도메인 조회에서 동일한 근거로 판정한다. 나중에 수정된 벌금 규칙으로 과거 결과를 재계산하면 안 된다.
- 면제·취소·재개방은 관리자 정정 사유와 원장을 남기는 정책이 필요하다. 이미 수령한 포인트를 화면에서 임의로 지우지 않는다.
- 월간 대상 주는 '주 시작일이 속한 월'로 통일하는 방안을 제안한다. 가입 전 주, 탈퇴 기간, 월을 걸친 주의 귀속을 서버에서 생성한 기대 주 집합으로 명시한다.

## 권장 구조

기존 경건·투표 UI는 재사용한다. 포인트 지급은 프론트 useReducer에서 실제 값으로 정산하지 않는다.

- 서버 `MissionQueryService`가 기존 경건·투표·멤버십·벌금 데이터를 판정해 상태와 이동 대상을 반환한다.
- 초기 버전은 서버 직접 조회로 시작한다. 프론트 이벤트는 재조회 신호일 뿐 완료 증거가 아니다.
- `MissionClaimService`는 수령 요청 시 다시 자격을 검증하고 미션 수령 원장과 포인트 원장을 동일 트랜잭션으로 기록한다.
- 같은 미션 재요청은 같은 결과를 반환한다. 동시 수령·모두 받기도 DB 고유 키와 트랜잭션으로 보호한다.
- 권장 초기 범위는 캠퍼스별 지갑·인벤토리. 현재 Provider도 사용자·캠퍼스·세션별로 초기화된다. 계정 전체 공용으로 바꿀 때는 캠퍼스별 중복 적립 정책을 먼저 정한다.
- 캠퍼스별 수령 고유 키: `(campus_id, user_id, mission_id, period_key)`. 포인트 원장에는 source type/id와 idempotency key를 둔다.
- 보유 수량·배치·배경은 서버에 저장한다. 배경 뽑기를 연결하면 보유한 배경만 적용할 수 있어야 한다.
- 뽑기 차감·확률 추첨·인벤토리 추가도 서버의 하나의 트랜잭션으로 처리한다. 판매는 마지막 한 마리와 동시 요청을 서버에서도 검증한다.

### 제안 API — 아직 존재하지 않음

| API | 역할 |
| --- | --- |
| GET /api/v1/campuses/{id}/companions/me | 포인트·보유·배치·배경 스냅샷 |
| GET /api/v1/campuses/{id}/missions/me?period=daily | 미션 상태·대상 날짜·수령 기한·이동 대상·serverNow |
| POST /api/v1/campuses/{id}/missions/me/attendance | 인증된 앱 방문을 한국 날짜 기준 한 번 기록 |
| POST /api/v1/campuses/{id}/missions/me/{missionId}/claims | periodKey 전달, 서버 자격 검증 후 수령 |
| POST /api/v1/campuses/{id}/missions/me/claims | 받을 수 있는 보상을 일괄 수령, 최신 스냅샷 반환 |
| PUT /api/v1/campuses/{id}/companions/me/garden | 배치·교체·위치·배경 저장, 보유·최대 5마리 검증 |

미션 응답 상태는 `incomplete / ready / claimed / settling / unavailable`로 구분한다. 네트워크 실패는 별도 error state로 표시한다. 조회 실패를 미완료나 보상 완료로 저장하지 않는다.

## 실제 연결 순서

1. 백엔드 미션 조회·수령·원장을 먼저 구현. 기존 경건·투표 저장 API의 응답 계약을 깨지 않는다.
2. 일간 출석·큐티·기도·말씀 → 주간 제출·투표 → 벌금 없음·월간 집계 순으로 연결한다.
3. 실제 앱 Provider에 인증된 API 스냅샷과 요청 중 잠금을 넣는다. 로그인·캠퍼스 변경 시 이전 요청 결과는 폐기한다.
4. 경건 빠른 체크 / 주간 저장 / 투표 응답 성공, 미션 페이지 진입, 앱 foreground 복귀 때 재조회한다. 자정·월요일 경계는 serverNow 기준으로 갱신한다.
5. 달성한 미션 배지와 '보상 받기'로 안내한다. 기존 화면에서 활동 저장 성공을 포인트 지급 성공으로 표시하지 않는다.
6. 네트워크 단절·재시도·동시 요청·이중 탭·두 기기 수령·한국 자정·전주 지연 제출·과거 기록 수정·투표 응답 수정·캠퍼스 전환·벌금 0 청구 행 없음·가입월·데이터 일부 조회를 검증한다.

현재 데모의 getDemoMissionStatus와 로컬 claim/draw/sell은 정식 경로에서 제거하고, 독립적인 디자인 미리보기에서만 남긴다. 백엔드가 준비되기 전에 실제 기록과 예시 보상을 섞어 정식 기능처럼 노출하지 않는다.
